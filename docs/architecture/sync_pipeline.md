# 同步流水线

本文说明数据从供应商接口到 PostgreSQL 的完整流程：注册表加载、任务规划、任务执行、写入、运行结束后的计算、定时调度，以及限速与单一执行进程。数据集配置的字段含义见 [数据集注册表格式](../interfaces/dataset_registry.md)，各张表的职责见 [数据库分层](data_model.md)，供应商接口的约定见 [同花顺接口](../interfaces/hithink_api.md)。

## 章节导航

- [总体流程](#pipeline_flow)：先读这一节。
- [代码结构](#code_structure)：新增或移动 `backend/src/sync/` 中的代码时。
- [波次规划](#waves)：修改规划器，或数据集之间有依赖时。
- [任务生命周期](#task_lifecycle)：修改认领、重试、失败处理时。
- [写入](#record_writes)：修改记录提取、写库、游标时。
- [运行结束后的计算](#postprocess)：修改复权重算、回补期间的定期重算或波次衔接时。
- [定时调度](#scheduling)：修改同步计划（每日、每周、每月、财报季）或触发规则时。
- [完整性核对与兜底补偿](#audit)：修改缺口核对、自动补偿，或想知道数据有没有丢时。

- [限速与单一执行进程](#rate_limit)：修改请求频率、全市场计算的并发，或想同时运行多个执行任务的进程时。
- [定期清理](#retention)：修改任务、调用日志的保留期限，或这两张表变大时。

<a id="pipeline_flow"></a>
## 总体流程

```
backend/config/datasets.yaml ─加载─► ops.dataset
        │ 规划器（按波次）
        ▼
   ops.run ─► ops.task ──执行器（SKIP LOCKED 认领，单进程多并发）──► 供应商 HTTP
                                    │                                   └─► ops.api_call（每次尝试一行）
                                    ▼
                 raw.record / raw.record_version（store_record 时）
                 ref.* / mkt.* / fin.*（sink）
                                    ▼
                  运行结束 ─► 复权重算 ─► 规划下一个波次
```

`niulai serve` 和需要数据库的运维子命令启动时先由 `bootstrap::bootstrap` 执行一次应用初始化：设置第一个管理员密码。随后创建同步引擎（`sync::Engine`）：读取并校验 `datasets.yaml`，把配置同步到 `ops.dataset`（配置中删掉的数据集标记为关闭，留作历史，数据集列表不再展示），创建供应商客户端和限速器。`Engine::new` 不执行鉴权或分析初始化，也不持有页面读取缓存等应用级资源：缓存由 `api::AppState` 创建，核心数据是否就绪按 `ops.dataset` 中各数据集的写入目标直接查（`readiness`），不依赖哪个进程执行过初始化。配置在进程启动时读取一次，修改配置后需要重启进程。

还没有配置 API Key 时，执行循环不认领任务、定时调度不发起增量，直到在网页上配置，见 [首次登录引导](../interfaces/rest_api.md#setup)。

规划和执行是解耦的：命令行、API、调度器都可以规划运行，任务都写进 `ops.task`，由 `niulai serve` 的执行循环（或 `niulai work`）执行。`niulai serve` 在一个进程中同时运行 API、执行循环和调度器，三者共用同一个同步引擎；`--no-api`、`--no-worker`、`--no-scheduler` 可关闭其中一部分。同一时刻只有一个进程执行任务，见 [限速与单一执行进程](#rate_limit)。

<a id="code_structure"></a>
## 代码结构

`backend/src/sync/` 按职责分层，上层依赖下层，同层模块互不依赖：

| 层 | 模块 | 职责 |
| --- | --- | --- |
| 入口 | `scheduler.rs`、`executor.rs`、`audit.rs`、`check.rs`、`retention.rs` | 同步计划与定时触发；执行循环、单个任务的编排和运行结束后的衔接；完整性核对与兜底补偿；数据核检；定期清理 |
| 事件 | `events.rs` | 发布同步运行完成和维护周期事件，不依赖分析、建议或鉴权模块 |
| 规划 | `planner.rs` | 把分区展开为任务，按波次创建运行 |
| 执行步骤 | `fetch.rs`、`records.rs`、`sinks.rs`、`postprocess.rs` | HTTP 取数与调用日志；记录主键与 `raw.record`；类型化表投影；运行结束后的计算 |
| 状态 | `queue.rs`、`run.rs`、`cursor.rs`、`calendar.rs` | `ops.task` 的状态变更；`ops.run` 的创建与结束；`ops.cursor`；`ref.trading_day` 与交易日校验 |
| 配置 | `spec.rs`、`template.rs`、`registry.rs` | 注册表的类型化表示、模板展开、同步到 `ops.dataset` |

任务状态迁移集中在 `queue.rs`；运行的创建、终态判定、接续和重开由 `run.rs` 负责，`planner.rs` 只更新规划过程的运行元数据（例如 `planning_error` 和 `planned_since_marks`）。重试、租约、推迟等时间策略是这两个模块和 `calendar.rs` 顶部的常量。

<a id="waves"></a>
## 波次规划

一次规划请求包含多个数据集。有些数据集依赖其他数据集的结果：按证券展开的数据集需要先有代码表，`from_dataset` 分区需要先有来源数据集的记录。规划器按依赖层级把数据集分成波次：

| 层级 | 分区类型 |
| --- | --- |
| 0 | `once`、`enum`，以及按自然日（`calendar: natural`）或接口日期列表（`dates_from`）展开的 `trading_day`（不依赖本地数据） |
| 1 | `security`、`security_batch`、`security_window`、`report_period`（依赖证券范围）；按本地交易日历展开的 `trading_day`（排在交易日历之后：第一次同步时日历还是空的，那时规划会把节假日当成交易日） |
| 来源层级 + 1 | `from_dataset`（来源数据集也有 from_dataset 时继续往上算，最多 8 层） |

规划时先创建第一个波次的 planning 运行，其余波次写入该运行的 `params.pending_waves`；API 返回运行编号后，后台再展开任务。后台规划每 30 秒刷新 `params.planning_heartbeat`，规划完成并写入全部任务后清除 planning 标记和心跳，执行者不会把空任务运行提前结束。维护按心跳超过 10 分钟判断规划是否中断，避免把正常但很慢的首次大回补误判为失败。一个波次的全部任务结束后，执行器先规划下一个波次，再做 [运行结束后的计算](#postprocess)，新运行的 `params.root_run` 指向第一个波次。接续时在创建新运行的同一个事务里清空前一个运行的 `pending_waves`（条件 UPDATE），所以下一个波次只会规划一次。结束 2 分钟以上、`pending_waves` 仍不为空的运行（接续时出错或进程退出）由维护组件每分钟补上。某个波次规划出 0 个任务时，立即结束该运行并规划下一个波次。

规划一个波次时，先算出所有数据集的任务，再在一个事务里创建运行、写入全部任务和任务总数。所以执行者看到一个运行时，它的任务已经齐全；否则前几个数据集的任务做完、后面的还在规划时，运行会被误判为已结束，下一个波次会提前开始。某个数据集规划失败（例如 universe 查询出错）时保留其他数据集的任务，但运行会记录 planning error，并在任务结束后显示为 `partial`，不能把未规划的数据集误报为成功。

`from_dataset` 分区的增量规划只看上次成功确认之后变化的来源记录。读取来源记录之前先记下数据库时刻，任务写入成功后把它保存到运行的 `planned_since_marks`；只有该运行全部任务成功后才提交到 `ops.cursor` 的 `part_key = '_plan'`。读取期间变化的记录下次还会被规划，失败运行不会把来源记录标记为已处理。

规划的选项有两个：
- `trade_date`：运行对应的交易日，默认今天，快照类数据集用它作主键的一部分。
- `only_thscodes`：只规划指定证券，作用于按证券展开的分区，用于重拉个别股票。

两个选项都写进运行的 params，在后续波次中保留。

任务按 `(dataset_id, part_key)` 去重：同一分区已有 `pending`、`running` 或 `failed` 状态的任务时，不会再创建一个。所以重复规划是安全的。主键里带 `{_run.trade_date}` 的数据集（按天积累的快照），`part_key` 末尾会加上 `|day=<运行交易日>`，不同交易日的任务互不去重；否则排队中的旧任务会挡住当天的增量。每种分区如何展开为任务，见 [分区类型](../interfaces/dataset_registry.md#partitions)。

<a id="task_lifecycle"></a>
## 任务生命周期

| 状态 | 含义 |
| --- | --- |
| `pending` | 等待执行 |
| `running` | 已被某个执行者认领，`locked_by` 记录执行者 |
| `done` | 成功，并写入了记录 |
| `empty` | 成功，但接口返回 0 条记录（例如停牌期间的窗口、非交易日），或返回了数据集 `empty_codes` 中声明的错误码（原因写在 `last_error`） |
| `skipped` | 主动跳过，原因写在 `last_error`：交易日校验判定不是交易日或在未来（见 [交易日校验](../domains/market_data_rules.md#trade_date_guard)）、日期已经不能用（见 [过期的日期](#stale_dates)），或人工标记 |
| `failed` | 可重试的失败，`not_before` 之后会被重新认领 |
| `dead` | 不再重试：不可重试的错误，或尝试次数达到 `max_attempts`（默认 4） |

交易日校验判定数据尚未就绪时，任务回到 `pending`，`not_before` 推迟 10 分钟，`attempts` 不增加，一直等到数据就绪。判定「已经错过」时记为 `dead`（错误信息以「已错过」开头），在同步页和完整性核对中显示。

执行者用一个短事务认领任务（实现在 `queue.rs`）：按 `priority, task_id`（部分索引 `task_claim_idx` 的顺序，积压再多也只读开头几行）取第一条 `pending` 或 `failed` 且 `not_before` 已到的任务，用 `FOR UPDATE SKIP LOCKED` 锁定，同时把 `attempts` 加 1。HTTP 调用在认领事务提交之后执行。完成、失败的更新都带 `locked_by = 当前执行者` 条件，超时被回收的旧执行者无法覆盖新结果。任务的 `priority` 按急迫程度分层，同一层再加上数据集的 P0 10、P1 20、P2 30、P3 40：

| 层 | 任务 |
| --- | --- |
| 0 | 定时同步中每个交易日执行的数据集（`schedule` 是 `daily`），包括只有当天值的估值、异动原因等 |
| 50 | 兜底补偿和数据核检的重取（`repair` 运行），以及补偿时重新排队的失败任务 |
| 100 | 定时同步中的其他数据集（每周、每月、财报季） |
| 200 | 历史回补 |

所以每周增量的几万个任务、积压的历史回补都不会挡住每天的数据。

失败处理分两层：
1. **单次请求内**：可重试的错误按 `defaults.retry.backoff_s`（默认 2、8、30 秒）退避后重试，每次尝试都写一行 `ops.api_call`。哪些错误可重试见 [错误处理](../interfaces/hithink_api.md#error_handling)。
2. **任务级**：重试用尽后，任务标为 `failed`，`not_before` 推迟 5 分钟 × 已尝试次数；尝试次数达到 `max_attempts`（默认 4，配置项 `defaults.retry.max_attempts`）后标为 `dead`。不可重试的错误（1xxx、2xxx、3001 等）、配置或解析错误直接标为 `dead`。

认领的任务带 10 分钟的租约。执行期间，执行者每分钟续租一次（刷新 `locked_at`），所以下载导出文件、长时间翻页这类超过 10 分钟的任务不会被当成崩溃。执行者崩溃后，任务停留在 `running`、不再续租。常驻服务的独立维护组件每分钟做一次维护，不论队列是否空闲；命令行 `niulai work` 由一个执行槽兼任维护：
1. 调用 `ops.requeue_stale('10 minutes')`，把租约过期的任务放回 `failed`；如果尝试次数已达上限，则标为 `dead`。
2. 找出状态仍是 `running`、但已经没有未完成任务的运行，把它结束。例如最后一个任务被回收后直接标为 `dead`，没有执行者处理过它，运行不会自己结束。
3. 回补期间定期重算复权因子，见 [运行结束后的计算](#postprocess)。

运行的状态：所有任务都结束（没有 `pending`、`running`、`failed`）时，有 `dead` 任务记为 `partial`，否则记为 `succeeded`。每个任务结束后，执行者先用部分索引 `task_run_open_idx` 判断所在运行是否还有未完成的任务；回补运行有二十多万个任务，这样不必每次统计整个运行。没有未完成的任务时，用带条件的 UPDATE 结束运行，只有一个执行者能成功，因此运行结束后的计算不会重复执行。

运行的 `tasks_done`、`tasks_failed` 在任务结束时累加，供查看进度；运行结束时再按任务表重新统计一次，纠正人工改动任务等原因造成的偏差。

<a id="record_writes"></a>
## 写入

一个任务的执行步骤：
1. 配置了 `trade_date_guard` 的数据集，在请求之前先做交易日校验，见 [交易日校验](../domains/market_data_rules.md#trade_date_guard)。
2. 取出任务的 `params.query`（已展开的请求参数），按配置的分页方式逐页请求。翻页在以下任一条件满足时停止：响应中 `data.pagination.has_next` 为 false；已到 `data.pagination.pages`；返回条数少于页大小。翻满 10,000 页但接口仍表示有下一页时任务失败，避免静默截断。全市场导出（`records: parquet`）先取预签名链接再下载 Parquet，下载失败时重新签名，最多 3 次。
3. 按 `records` 路径取出记录。路径缺失或类型不是数组/对象时任务失败；路径存在但值为 `null` 才按空结果处理。按主键模板生成 `rkey`、`thscode`、`obs_date`，见 [主键与模板](../interfaces/dataset_registry.md#keys_and_templates)。
4. `store_record` 为 true（默认）时，每 2,000 条调用一次 `raw.upsert_records`：值未变化只刷新 `last_seen_at`，值变化时先把旧值写入 `raw.record_version`。
5. 依次执行配置中的每个 `sink`，写入类型化表。所有 sink 都是幂等的 UPSERT。
6. 推进进度游标 `ops.cursor`：`security_window` 分区按证券记录连续成功的窗口末日，`trading_day` 分区记录连续成功的日期；只沿连续成功前沿前进。增量规划从游标往后算。

raw 记录、类型化 sink 和游标在同一个任务事务中写入；事务开始时锁定并确认当前任务租约，租约失效的 worker 不能提交这组副作用。

任务的 `records` 是返回的记录数，`changed` 是新增或值变化的记录数（`store_record` 为 false 时是 sink 写入的行数）。

游标按连续成功前沿推进：并发窗口或交易日任务只能在前面的窗口已经成功（`done` 或 `empty`）时继续推进；后面的任务先完成不会越过仍待重试的前置任务。租约失效后，执行器在取数和每个写入边界重新确认任务仍归当前 worker 所有，失去租约的 worker 不应继续产生新的副作用。

<a id="postprocess"></a>
## 运行结束后的计算

运行结束时，如果影响复权价的数据集有变化（`sink` 中有 `mkt.stock_bar_1d` 或 `mkt.corp_action` 的数据集，见 `spec.rs` 的 `PRICE_TABLES`）（成功任务的 `changed` 合计大于 0），依次执行：
1. 把个股日线和 ETF 日线中出现过的日期补进 `ref.trading_day`（来源记为 `derived`）。供应商日历只有最近一年。
2. `CALL mkt.rebuild_adj_segment(run_id)`：全量重算复权分段，包括等比复权因子和同花顺减法复权的系数。本机全市场实测约 2 秒（1,500 万根日线、6 万段分段；第一次执行或磁盘忙时会更久），在数据库事务中完成，查询在提交前看到旧结果，不被阻塞。
3. 更新 `ops.derived_version` 的 `adj_factor` 行，使依赖复权价的缓存（市场概况、账户的因子排名）失效；配置 Redis 时，共享读取缓存也因版本键变化而切换到新结果。

**同步完成事件分阶段持久化。** 事件写在 `ops.run.params.sync_event_pending`，有两个阶段：

| 阶段 | 什么时候写 | 谁处理 |
| --- | --- | --- |
| `postprocess` | `try_complete` 把运行置为终态的同一条条件 UPDATE 中写入，带后处理的租约 `claimed_at` | 结束运行的执行者接着做后处理；它出错或进程中途退出、租约（5 分钟）过期后，维护组件抢占并重做（`run::claim_stale_postprocess`，重算是幂等的） |
| `ready` | 后处理做完，带上准确的 `price_changed` | 应用事件编排器（`bootstrap`） |

应用层只消费 `ready` 的事件，所以不会在复权重算之前用旧价格生成建议。没有任务的运行直接写 `ready`。

**应用层处理。** 编排器收到 `SyncRunCompleted`（或每分钟的 `MaintenanceTick`）后，读出全部 `ready` 的事件一起处理：

1. 汇总这一批全部运行的影响：任一运行的价格类数据有变化；三个权威涨跌停池（`special.limit_up_pool`、`limit_down_pool`、`limit_break_pool`）有变化条数时更新 `ops.derived_version` 的 `limit_pool` 行；因子的非价格输入（三张季度财报，以及写行业成分、证券信息的数据集，见 `factor_lab::INPUT_DATASETS`、`INPUT_TABLES`）有变化时更新 `factor_input` 行。涨跌停池只写 `raw.record`、没有类型化表，不在 `PRICE_TABLES` 里，所以单独判断；**即使行情没有变化，只要池补上了滞后的数据也会更新**。
2. 三者任一有变化时，为每个账户重新生成 [调仓建议](../domains/accounts.md#generation)（在后台计算的槽位里）。某个账户失败时转成它的重算待办，由建议重算组件重试，不让事件一直挂着。
3. 只确认这一批里的运行（按运行编号删除标记），不按编号范围整段清除：处理期间新到的、还在后处理的事件留到下一次。

处理失败时不确认，下一次事件或维护重放；建议失败不会让后面的波次停掉。缓存都按 `ops.derived_version` 的版本失效（市场概况和今日热点看 `adj_factor`、`limit_pool`，账户的因子排名看 `adj_factor`、`factor_input`），不靠某个进程收到事件后去清空，所以 `niulai recompute` 和多个进程并存时也不会用到旧结果。执行循环每分钟发布 `MaintenanceTick`，编排器消费后在没有增量同步运行时补齐缺的建议，每天清理一次被取代的建议，不运行任何回测。下一个波次在事件发布之前就已规划。复权的计算规则见 [复权](../domains/price_adjustment.md)。

新的一天的日线不用重算就有复权价（落在最后一个分段里）。但一个回补运行可能要执行一两天，期间补回来的历史日线和公司行动会改变分段，只在运行结束时重算的话，这段时间的复权价是旧的。所以维护组件（每分钟一次）还会检查：自上次重算以来有价格类任务写入了变化，并且距上次重算超过 5 分钟，就重算一次。上次重算的时刻记在 `ops.scheduler` 的 `adj_rebuild` 作业上，用条件 UPDATE 抢占；运行结束时的重算也会刷新这个时刻。重算不阻塞查询，见 [等比复权因子](../domains/price_adjustment.md#equal_ratio_factor)。

<a id="scheduling"></a>
## 定时调度

`niulai serve` 默认启动调度器（`--no-scheduler` 或 `NIULAI_SCHEDULER_ENABLED=false` 可关闭）。每个数据集按配置中的 `schedule` 归入一个同步计划，实现在 `scheduler.rs`：

| 同步计划 | `schedule` | 什么时候同步 |
| --- | --- | --- |
| 每日收盘后 | `daily`（不写时的默认值） | 每个交易日到了每日时间（默认 18:00） |
| 每周 | `weekly` | 每周到了每周的星期和时间（默认周六 08:00），不论是不是交易日 |
| 每月 | `monthly` | 每月第一次每周同步时，一起同步 |
| 财报季 | `report_season` | 1、4、7、8、10 月随每日同步，其余月份随每周同步 |
| 不自动同步 | `manual` | 只手动发起 |

**时间：** 都是上海时间，见 [时区](../interfaces/configuration.md#time_zone)。每日时间、每周的星期和时间可以在同步页上修改，保存在 `app.setting` 的 `sync_schedule` 行（JSON：`daily_time`、`weekly_weekday`、`weekly_time`），调度器每 30 秒检查时重新读取，不用重启。网页上没有改过时，每日是 18:00，每周是周六 08:00。每周默认放在周末，几万个任务不和每日数据抢请求额度。

调度器每 30 秒检查一次：

1. **每日：** 上海时间已到每日时间、当天是周一到周五，并成功抢占 `ops.scheduler` 中的 `daily` 作业（条件 UPDATE 把 `last_fired` 推进到今天，多个进程并存时也只有一个成功）。再现取交易日历并写入 `ref.trading_day`，今天是交易日才规划。日历取不到时退回本地记录；本地日历还没有覆盖到今天时按交易日处理，快照的交易日校验会兜底。运行的交易日是今天。
2. **每周：** 算出不晚于现在的最近一个每周时刻，`weekly` 作业的 `fired_at` 早于这个时刻就抢占并触发。所以服务在那个时刻停机，启动后立即补上；改了每周时间，下一个时刻起按新时间。第一次（还没有 `weekly` 这一行）只记下现在、不触发：刚部署的系统正在做首次回补。触发时再按自然月抢占 `monthly` 作业，抢到就把每月的数据集一起规划。运行的交易日是最近一个交易日，按天积累的数据（例如指数成分）记在这一天。

抢占之后的步骤（取交易日历、规划）出错时，把这些作业的水位恢复成抢占之前，下一次检查重试，不会因为一次数据库抖动丢掉这一天或这一周的同步；补发也一样。

每次运行在 `params.trigger` 记下谁发起的，同步记录据此显示来源：`daily`、`catch_up`（补发每日同步）、`weekly`、`weekly+monthly`、`manual`（网页上发起）、`setup`（首次补历史）、`cli`（命令行）、`repair`（兜底补偿）、`data_check`（数据核检重取缺口）。没有这个字段时按 `kind` 显示。

**补发：** 调度器每 30 秒还会检查上一个交易日（10 天以内）的每日同步有没有发起过。例如那天到点后服务一直没有运行，就立即为那一天补发一次，只包括每日同步的数据集。只有当天值的数据还能不能取到由交易日校验决定：下一个交易日的数据出来之前补发就能取到，之后会记为「已错过」。系统还没有开始每日同步时（`ops.scheduler` 中没有 `daily`）不补发。

**同步计划总览：** `GET /api/v1/sync/schedule` 返回时间设置，以及每个计划的规则、包含的已开启数据集、下次同步时刻和上次同步（发起时刻、运行和状态，状态包括后续波次）。`PUT` 修改时间。

手动触发：同步页上可以按计划勾选或全选后增量同步或全部重取，每个计划也有「现在同步一次」。命令行 `niulai daily` 只规划每日同步的数据集。

<a id="audit"></a>
## 完整性核对与兜底补偿

实现在 `audit.rs`，接口是 `GET /api/v1/sync/health`（同步页顶部的状态和「需要注意」）和 `POST /api/v1/sync/repair`（「立即补齐」）。

**核对范围：** 从开始每日同步的那天起，最近 20 个已经到了同步时间的交易日。

**缺口：**

| 类型 | 判定 | 能否补回 |
| --- | --- | --- |
| `not_run` | 每日数据集在这一天没有任何任务，或任务被跳过（不是因为非交易日） | 有历史的数据集能补；只有当天值、没有 `recover_with` 的，只在供应商还停在这个交易日时（周末、下一个交易日开盘前）能补，之后补不回来 |
| `missed` | 只有当天值的数据集被交易日校验判定「已错过」 | 补不回来 |
| `failed` | 有任务失败（`dead`），而且这个分区之后没有成功过 | 同上 |
| `incomplete` | 个股日线的条数少于这一天在市股票数的 97%（停牌的股票没有日线，通常不到 2%） | 能补：只补缺日线的股票 |

同一个分区在任何一次运行中成功过就算成功，所以失败后已经补上的不再算缺口。核对看定时同步和补偿运行的任务；回补运行里按天积累的快照（分区键带 `|day=<交易日>`）也算，因为首次部署时回补和每日同步同时规划，同一个分区按去重只有一个任务。

判断「供应商还停在这个交易日」要查一次供应商最新交易日（进程内缓存 10 分钟）。这次查询和同步任务共用限速，最多等 2 秒，没等到时按补不回来显示，查完后下一次刷新再更新。

**失败的任务：** 失败（`dead`）而且这个分区之后没有成功过的任务（视图 `ops.v_unresolved_dead`，同步页的失败计数、这里的失败列表、兜底补偿的重排和定期清理都按它判断），按数据集和错误分组，附白话说明：已错过、日期不是交易日、超出接口的历史范围、接口不支持这个代码、写入数据库失败（程序问题）、供应商暂时不可用。

**兜底补偿：**
1. 能补的缺口，按数据集规划 `repair` 运行：用数据集本身，或它的 `recover_with`（收盘快照由个股日线补，指数快照由指数日线补）。个股日线只补缺日线的股票。补偿与增量的规划规则相同，从游标往后取。
2. 因为供应商暂时不可用、重试用尽而失败的任务（错误信息以「可重试错误」开头），每个分区重新排队最新的一个，放到 50 层，再试一次。所在的运行重新打开，任务结束后照常结束；已经接上的后续波次不会再规划（见 [波次](#waves)）。同一个任务最多这样补偿 3 次（`ops.task.repairs`）：供应商一直给不了的分区（例如某个历史日期一直返回 5003）不会每天被重排、把运行重新打开。
3. 按交易日分区、日期其实不是交易日或已经超出接口历史范围的失败任务（见 [过期的日期](#stale_dates)），改为跳过（`skipped`），不再作为失败列出。已推断退市（`ref.instrument.delisted_on` 不为空）的证券因 1002（不认这个代码）或 3004（不给行情）失败的任务也改为跳过，错误信息写明退市日期：退市前排队或自动推断退市之前留下的这些失败补不回来。
4. 补不回来的缺口只列出，不处理。

**自动执行：** 调度器在最近一个交易日的每日同步发起之后、所有每日和补偿任务都结束时执行一次补偿，每个交易日最多一次（抢占 `ops.scheduler` 中的 `repair` 作业）。同步页的「立即补齐」随时可以执行，不影响当天的自动补偿。

<a id="data_check"></a>
## 数据核检

[完整性核对](#audit) 只看最近 20 个交易日、按全市场条数判断，个别股票缺了某天、更早的历史有洞都查不出来。数据核检逐只证券、逐个交易日对照个股日线（`a_share.bar_1d` → `mkt.stock_bar_1d`）、ETF 日线（`fund.etf_bar_1d` → `mkt.etf_bar_1d`）和指数日线（`index.bar_1d` → `mkt.index_bar_1d`），实现在 `check.rs`：

1. **范围：** 数据集 universe 中的证券，从数据集起点（`floor`）和上市日中较晚的一天起（不知道上市日的指数从第一条日线起，一条都没有就不查），到今天之前最近的一个交易日；已推断退市的证券（`ref.instrument.delisted_on`）只查到退市日前一天，之后供应商不再认这个代码，算成缺口只会每次都重取失败。交易日以 `ref.trading_day` 为准：近一年来自供应商日历，更早的是行情里出现过的日期。正在同步的证券（这个数据集有未完成的任务，例如还在首次回补）先不查，等它同步完。
2. **缺口：** 交易日里有、日线表里没有的「证券 × 交易日」，写入 `ops.bar_gap`（状态 `open`）。以前记下的缺口这次有数据了，删掉，记为「已补回」。
3. **重取：** 还缺、没有安排过重取（或上次重取的运行已经结束、没能确认）的缺口，同一只证券合并成一个窗口（从最早的缺口到最晚的缺口；一次请求最多取 10 年，按窗口算请求量很小，散落的停牌日一天一个窗口的话，全市场第一次核检要上万次请求），规划一次 `repair` 运行（`params.trigger = data_check`，排在补偿那一层），只取这些窗口。
4. **确认停牌：** 供应商停牌日不返回日线，单看缺口分不清漏了还是停牌。发现缺口之后，有覆盖这一天的任务成功结束（`done` 或 `empty`，重取任务、回补任务都算），这一天仍然没有日线，就确认是停牌（状态 `suspended`），以后不再报、不再重取。

**什么时候跑：** 最近一次每周同步的各批全部结束后，每周一次（抢占 `ops.scheduler` 的 `data_check` 作业）；重取的运行结束后再复查一次，确认结果（与上次核检至少隔 10 分钟）。同步页的「立即核检」和 `niulai check` 随时可以执行。核检在后台执行，同时只做一次：独占权是数据库咨询锁 `niulai.data_check`，用一个独立连接持有，多个进程之间也互斥，进程退出时自动释放；接口先取锁再交给后台任务，取不到时返回 409。每次核检的结果写入 `ops.data_check`：每个数据集查了多少证券和「证券 × 交易日」、新发现、已补回、本次和累计确认停牌、仍缺、重取的运行和任务数。

<a id="stale_dates"></a>
## 过期的日期

按交易日分区（`trading_day`）的任务从规划到执行可能隔很久（回补排在每日数据后面，要一两天），日期可能已经不能用了。执行前用 `calendar::stale_partition_date` 再确认一次，以下情况直接跳过，不请求接口：

- **超出历史范围：** 日期早于分区的 `from` 按今天重新算出的起点。例如 `from: -1y` 的数据集，接口只接受一年内的日期（否则返回 1003 date must be within one year），排队期间滑出一年的任务跳过。
- **不是交易日：** 周末，或供应商日历覆盖了这一天却没有它。只对按本地日历展开的分区判断；按自然日查询的数据集（`calendar: natural`）本来就要查节假日。日历还没覆盖到的日期不下结论。

兜底补偿用同一个函数清理已经因为这两种原因失败的任务，见 [完整性核对与兜底补偿](#audit)。

<a id="rate_limit"></a>
## 限速与单一执行进程

供应商 API Key 有全局请求频率上限，多开进程不会更快，所以同一时刻只允许一个进程执行同步任务：`niulai serve` 的执行循环或 `niulai work` 启动前，用一个独立的数据库连接取得咨询锁 `pg_try_advisory_lock(hashtext('niulai.executor'))`，取不到时 `niulai work` 报错退出，`niulai serve` 先只提供 API、每 30 秒再试（宿主机崩溃后，数据库可能要过一阵才发现旧连接断了），不让整个进程反复重启。进程退出、连接关闭时锁自动释放。持锁期间每 30 秒在这个连接上执行一次 `SELECT 1`：连接断了（数据库重启、网络中断）锁已经被释放，别的进程可能接手，于是停止认领、等在途任务结束后按故障退出，由 Docker 重启后重新取锁。`niulai serve --no-worker` 不取锁，可以另外启动。

全市场计算（市场概况、因子研究、账户的因子排名）同时最多 2 个，多出来的排队；后台任务（调仓建议、页面预热）另有一个槽位，页面上同时开几个因子研究也不会让它排不上。

限速在进程内：每次请求前检查最近 1 秒内的请求数，达到**当前速率**时等到最早那次请求满 1 秒。

`NIULAI_RATE_LIMIT_RPS`（默认 2）是**速率上限**，不是死值：供应商返回 429（HTTP 429 或错误码 4001）时，速率立刻降到当前值的一半（最低 1 次/秒）；之后每连续成功 40 次回升 1，直到重新抵达配置的上限。这样限速宽松的 Key 能自动跑满，限速严格的 Key 又不会一直撞 429。网络错误、服务端 5xx 这类与被限速无关的失败不参与调整。

当前速率显示在网页「数据同步」页；`GET /api/v1/sync/health` 的 `rate.current` / `rate.ceiling` 也能读到，两者不相等说明正在被限流。

`niulai plan`、`niulai daily` 规划时偶尔请求几次接口，不取锁，会与执行循环短暂叠加。全市场计算按 128 只证券一批读取，数据库事务在 CPU 计算前提交，避免长时间占用连接和快照。为什么不用 Redis 跨进程限速，见 [ADR：限速在进程内](../decisions/in_process_rate_limit.md)。

单个进程同时执行的任务数由 `NIULAI_WORKER_CONCURRENCY`（默认 3）控制。实测每秒 2 次、并发 3 的强度下没有触发供应商限流，实际吞吐约每秒 1.7 次。

**全市场计算：** 市场概况、因子研究和账户的因子排名要逐只股票读出日线再计算，一次要几秒到十几秒的 CPU。预算在 `analysis/compute.rs`：入口用 `compute::run` 显式声明前台（`Budget::Foreground`，同一进程最多 2 个，`FOREGROUND_SLOTS`）还是后台（`Budget::Background`，1 个），其余排队，避免几个页面同时打开时把 CPU 和连接池占满。槽位按用例持有：一次因子研究从读财报、行业和日线，到检验、组合模拟、写运行记录都占着同一个槽位，「最多 2 个」就是最多 2 个完整任务；同一个任务里嵌套的 `compute::run`（例如后台建议里读市场概况、算排名）复用已经拿到的槽位。逐只股票的计算用 `compute::run_cpu`（`block_in_place`）执行，不占住处理 API 请求的异步线程。

**组件监督：** `niulai serve` 中的 API、执行循环、调度器、应用事件、建议重算和页面预热（配置 Redis 时）是同一进程里的几个组件。任何一个提前退出（出错或 panic），进程通知其余组件停止，然后以非零状态退出，由 Docker 的 `restart: unless-stopped` 或 systemd 重新启动；不会出现 API 还在、同步已经停了的半死状态。API 处理函数启动、不等结束就返回的后台任务（后台规划、立即核检）登记在 `AppState::background`，失败统一写日志，停机时和组件一起在期限内收尾，超时取消；被取消的规划由维护按心跳结束为失败，被取消的核检下次标记为「没有做完」。

<a id="retention"></a>
## 定期清理

`ops.task` 和 `ops.api_call` 每天都在增长：一次全量回补几十万个任务，每次请求一行日志。执行循环的维护每天做一次清理（抢占 `ops.scheduler` 的 `prune` 作业），实现在 `retention.rs`，分批删除（每批 2 万行）避免长时间锁表：

- 结束超过 60 天、之后同一分区已经成功过的失败任务（问题已经解决，即不在 `ops.v_unresolved_dead` 里）。还没解决的失败一直保留，兜底补偿和同步页还要用。
- 结束超过 60 天的成功、没有数据、跳过的任务；进行中的运行里的任务不删，每个数据集最近一个成功的任务保留（「最近同步」从它来）。
- 超过 30 天的调用日志（按 `called_at` 索引删）。

被重新生成取代超过 30 天、没有处理记录的调仓建议不在这里清理，由 `advice` 自己每天清理一次（抢占 `ops.scheduler` 的 `advice_prune` 作业），见 [生成建议](../domains/accounts.md#generation)。
